# tools.molyuk.com

Набор повседневных инструментов разработчика: генерация ID, хэши, base64 и другое.
Почти всё считается локально в браузере. Исключения — «Мой IP» и «DNS запрос»
(`compute: 'edge'`): первому нужен воркер, чтобы увидеть адрес клиента, второму —
чтобы сходить к резолверу.

Стек: Vue 3 + Vite + TypeScript + Tailwind CSS. Интерфейс двуязычный (ru/en) на vue-i18n.
Деплой — Cloudflare Workers: воркер отдаёт статику и обслуживает `/api/ip` и `/api/dns`
(`worker/index.ts`).

## Разработка

```sh
npm install
npm run dev
```

## Добавление нового инструмента

Каждый инструмент — папка в `src/tools/<slug>/` с файлом `index.ts`:

```ts
import { defineAsyncComponent } from 'vue'
import type { ToolMeta } from '../types'

export const meta: ToolMeta = {
  slug: 'my-tool',
  nameKey: 'tools.myTool.name',
  descriptionKey: 'tools.myTool.description',
  categoryId: 'converters',
  order: 14,
  compute: 'client',
}

export const component = defineAsyncComponent(() => import('./MyTool.vue'))
```

Поля `ToolMeta` (`src/tools/types.ts`):

| Поле             | Значение                                                                       |
| ---------------- | ------------------------------------------------------------------------------ |
| `slug`           | Имя папки; она же путь верхнего уровня `/<slug>`                               |
| `nameKey`        | Ключ i18n для названия — не сам текст                                          |
| `descriptionKey` | Ключ i18n для описания                                                         |
| `categoryId`     | `identifiers` \| `encoding` \| `text` \| `network` \| `converters` \| `data`   |
| `order`          | Сквозной номер по всему сайту — виден на карточках главной как `01`, `02`, …   |
| `compute`        | `client` (в браузере) или `edge` (нужен воркер)                                |

Инструмент автоматически появится в навигации и на главной странице (`src/tools/registry.ts`
сканирует папку через `import.meta.glob`) — роутер и меню трогать не нужно.

Слаг — это путь верхнего уровня (домен уже называется `tools.`, поэтому префикса `/tools/`
нет). Значит, слаг не должен совпадать с тем, что перехватывается раньше SPA: `api`
(ручки воркера), `assets` и имена файлов из `public/`. Генератор списка маршрутов
(см. ниже) падает со сборкой, если слаг задублирован или занят.

### Маршруты и настоящий 404

Воркер обязан знать, какие пути настоящие, иначе на опечатку он ответит 200 с текстом
«не найдено» — так называемый soft-404, который поисковики индексируют как обычную
страницу. Импортировать реестр воркер не может: тот тянет за собой Vue-компоненты.
Поэтому `scripts/generate-worker-routes.mjs` собирает список слагов в `worker/routes.ts`.

Файл **сгенерированный, править руками не нужно** — он перезаписывается на каждой сборке
(`prebuild` в `package.json`), а `npm run deploy` начинается со сборки, так что
задеплоить устаревший список нельзя. В репозитории он лежит, чтобы `wrangler dev`
работал на свежем клоне без предварительной сборки.

Отсюда же `not_found_handling = "none"` в `wrangler.toml`: со значением
`single-page-application` ассет-сервер сам возвращал бы оболочку с кодом 200, и воркер не
смог бы отличить промах от попадания.

### Про `order`

Номер отображается пользователю, и внутри категории инструменты идут по нему же.
Поэтому нумерация должна оставаться **сплошной от 01** и сгруппированной по категориям
в порядке `CATEGORY_ORDER` из `registry.ts`. Вставка инструмента в середину означает
сдвиг номеров у всех, кто идёт после, — это одна строка в каждом `index.ts`.

### Строки интерфейса

Тексты живут в `src/i18n/messages.ts` — блок `tools.<camelCaseSlug>` нужно добавить
**в обе локали, `ru` и `en`**. Тип `MessageSchema` выведен из `ru`, так что забытый
английский ключ ловится `vue-tsc` на сборке; забытый русский — нет, он просто
отрендерится как сырой ключ. Ключи, которые шаблон собирает динамически
(например `` t(`tools.cidr.scope_${scope}`) ``), тайпчекер не проверяет вовсе —
их стоит перепроверить руками.

### Компонент

Компонент инструмента оформляется в `<slug>/<Name>.vue` и собирается из общих блоков
в `src/components/`:

| Компонент          | Назначение                                                          |
| ------------------ | ------------------------------------------------------------------- |
| `ToolPage.vue`     | Обёртка страницы: заголовок, описание, отступы                      |
| `ToolPanel.vue`    | Панель параметров над результатом                                   |
| `OutputBar.vue`    | Полоса «Вывод» со статусом и кнопками копирования/скачивания        |
| `CopyButton.vue`   | Копирование в буфер (опционально вместе с картинкой)                |
| `DownloadButton.vue` | Скачивание результата файлом                                      |

Чистую логику (парсинг, арифметику) лучше держать в отдельном `.ts` рядом с компонентом —
так её можно переиспользовать и проверить. Примеры: `src/tools/ip-list/ip.ts` с разбором
IPv4/IPv6, который использует и генератор списков, и CIDR-калькулятор;
`src/tools/color/color.ts` с матрицами OKLab.

Если инструмент выполняет то, что ввёл пользователь (регулярное выражение, шаблон, формулу),
это должно уходить в Web Worker с таймаутом — см. `src/tools/regex/`. Регулярку нельзя
прервать: `(a+)+b` на тридцати символах считается около минуты, и в основном потоке это
намертво вешает вкладку. Из воркера поток можно просто убить.

## Тесты

```sh
npm test               # все наборы из tests/, с итогом по числу проверок
node tests/run.mjs --verbose   # с полным выводом каждого набора
```

Наборы лежат в `tests/*.test.mjs` и импортируют **настоящие исходники**, а не копии:
копия свободна разъехаться с кодом, и тогда зелёный прогон перестаёт что-либо значить.
Node не резолвит импорты без расширения так, как это делает Vite, поэтому раннер
подключает хук `tests/ts-resolve.mjs`.

Общие утверждения — в `tests/harness.mjs`: намеренно крошечный и без зависимостей,
потому что тест-раннер, который надо ставить, стал бы первой зависимостью в проекте.
Каждый набор запускается отдельным процессом: они правят глобальное состояние
(полифилл crypto, заглушки браузерных API), и в общем процессе настройка одного набора
молча удовлетворяла бы требования другого.

Число проверок пишется в `src/generated/tests.json` и показывается на главной. Оно
получается из реального прогона, а не вписано руками — `prebuild` запускает `npm test`,
так что собрать с красными тестами нельзя, а счётчик на странице не может соврать.

## Сборка и деплой

```sh
npm run build          # генерация routes.ts + тесты + проверка типов + сборка в dist/
npm run worker:dev      # локальный запуск как Cloudflare Worker (wrangler dev)
npm run deploy          # сборка + wrangler deploy
```

Сборка теперь занимает ~8 секунд вместо ~0.3: почти всё это прогон тестов. Это
осознанный размен — деплой не должен проходить с красными тестами. На `npm run dev`
не влияет.

`worker:dev` поднимает воркер вместе со статикой — это единственный способ проверить
маршрутизацию и коды ответов локально: `vite preview` отдаёт 200 на любой путь и про
404 ничего не знает.

Деплой требует авторизации в Cloudflare: `npx wrangler login`.
